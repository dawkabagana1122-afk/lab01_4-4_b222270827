# Лаб 1: UI автомат тест — Playwright

**F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)**

[saucedemo.com](https://www.saucedemo.com) демо дэлгүүрийн нэвтрэх хэсгийг Playwright (TypeScript) ашиглан автоматаар тестэлсэн ажил.

## Юу хийсэн бэ

1. `npm init playwright@latest` командаар TypeScript төсөл үүсгэж, Chromium, Firefox, WebKit гурван хөтөч суулгасан.
2. [`playwright.config.ts`](playwright.config.ts)-д `baseURL`-ийг тохируулсан. saucedemo `data-test` attribute ашигладаг тул `testIdAttribute`-ийг түүнд тааруулсан. Мөн тест бүрийн **trace** болон **video**-г хадгалахаар тохируулсан.
3. [`tests/mytest.spec.ts`](tests/mytest.spec.ts) файлд 3 тест бичсэн. Тест бүр гурван хөтөч дээр ажилладаг тул нийт 9 удаа ажиллана.

| # | Тест | Шалгах зүйл |
|---|------|-------------|
| 1 | Амжилттай нэвтрэх | `standard_user / secret_sauce`-аар нэвтрэхэд `/inventory.html` руу шилжиж, "Products" гарчиг болон бараанууд харагдана (`toHaveURL`, `toBeVisible`, `toHaveText`) |
| 2 | Амжилтгүй нэвтрэх (сөрөг тест) | Буруу нууц үг оруулахад `alert` элемент дотор алдааны мессеж гарч, хэрэглэгч нэвтрэх хуудсан дээрээ үлдэнэ |
| 3 | Бараа сагслах | "Sauce Labs Backpack"-ийг сагсанд нэмэхэд товч нь "Remove" болж, сагсны тоолуур 1 болно. Сагсны хуудсан дээр яг тэр бараа харагдана |

- Нэвтэрсэн тест бүр **Logout**-оор төгсдөг бөгөөд гарсны дараа нэвтрэх хуудас руу буцсаныг шалгадаг.
- Тест бүр шинэ browser context-оор эхэлдэг (`beforeEach`). Тестүүд бие биеэсээ хамааралгүй тул `fullyParallel` горимд зэрэг ажиллаж чадна (**test isolation**).
- Тестүүдийг `--repeat-each=5` тохиргоогоор 45 удаа ажиллуулж тогтвортой ажиллаж байгааг шалгасан.

## Ажиллуулах

```bash
npm install
npx playwright install        # хөтөчүүдийг суулгана
npx playwright test           # бүх тест (3 хөтөч × 3 тест = 9)
npx playwright show-report    # HTML тайлан нээнэ
npx playwright show-trace report/traces/03-baraa-sagslah-trace.zip   # trace үзэх
```

## Тайлан, бичлэг (`report/`)

- [`report/html-report/`](report/html-report/) — Playwright HTML тайлан. Тест бүрийн бичлэг болон trace нь дотор нь багтсан. Үзэхийн тулд `npx playwright show-report report/html-report` командыг ажиллуулна.
- [`report/videos/`](report/videos/) — Chromium дээр тест бүр ажиллаж буй дүрс бичлэг (`.webm`).
- [`report/traces/`](report/traces/) — Тест бүрийн trace файл. `npx playwright show-trace <файл>` командаар эсвэл [trace.playwright.dev](https://trace.playwright.dev) сайтад чирж оруулж үзнэ.

## Яагаад XPath биш, орчин үеийн locator вэ?

`getByRole`, `getByText`, `getByPlaceholder`, `getByTestId` нь элементийг **хэрэглэгчид харагдах шинжээр** нь (роль, нэр, текст) олдог. `//div[2]/form/div[3]/input` маягийн XPath нь хуудасны DOM бүтцээс шууд хамаардаг. Дизайнер нэг `div` нэмэхэд л тест эвдэрдэг, мөн юуг шалгаж байгааг уншихад хэцүү. `getByRole('button', { name: 'Login' })` нь DOM өөрчлөгдсөн ч хэрэглэгчид "Login" товч харагдсаар байвал ажилласаар байна. Мөн хандалтын мод (accessibility tree) дээр тулгуурладаг тул сайт хүртээмжтэй (accessible) эсэхийг давхар шалгадаг.

## Playwright ба Selenium — миний ажиглалт

Playwright-ийн хамгийн мэдэгдэхүйц давуу тал нь **auto-wait** юм: би нэг ч `sleep` эсвэл explicit wait бичээгүй. `click()` болон `expect()` нь элемент бэлэн болтол өөрөө хүлээсэн. Selenium дээр бол `WebDriverWait` бичих шаардлагатай байдаг. Суулгалт ч хялбар байсан: `npx playwright install` нэг командаар гурван хөтчийг суулгасан, хөтөч бүрд тусад нь driver татах шаардлагагүй. Гурван хөтөч дээр зэрэг ажиллуулахад ч нэмэлт тохиргоо хэрэггүй, `projects` хэсэгт зааж өгөхөд л хангалттай. Trace viewer дебаг хийхэд маш хэрэгтэй байсан. Тест унах үед алхам бүрийн DOM snapshot-ыг харахад "Logout" нь link биш **button** гэдэг шууд харагдсан. Selenium-ийн ердийн лог, скриншотоос ийм мэдээлэл олоход илүү хэцүү. Харин Selenium-ийн давуу тал нь олон жилийн туршид тогтсон экосистем, хэлний өргөн сонголт, Selenium Grid зэрэг том дэд бүтэц юм. Олон хуучин төслүүд Selenium дээр бичигдсэн байдаг тул аль алиныг нь мэдэх нь чухал.

## Codegen ба Trace viewer

- `npx playwright codegen https://www.saucedemo.com` — хөтөч дээр хийсэн үйлдлийг шууд код болгодог. Codegen ч мөн `getByRole`, `locator('[data-test=...]')` зэрэг locator сонгодог. Гэхдээ assertion бараг нэмдэггүй, бүх үйлдлийг нэг урт тест болгодог. Өөрийн бичсэн тест маань давтагдах алхмыг `login()`, `logout()` функц болгож, үйлдэл бүрийн дараа үр дүнг `expect`-ээр шалгадаг.
- Тестийг санаатайгаар унагахын тулд хүлээгдэж буй текстийг `'Products'`-аас `'Product'` болгож өөрчилсөн. Trace viewer дээр унасан алхам улаанаар тодорч, тухайн агшны DOM snapshot дээр бодит текст "Products" байгааг харж алдааг хурдан олсон.

## Нэмэлт даалгавар: AI-ийн өнцөг

Энэ лабын тестүүдийг бичихэд AI туслах (Claude Code) ашигласан бөгөөд үр дүнг өөрөө ажиллуулж, шалгаж зассан. (1) AI-ийн анхны хувилбар зааварт байгаа жишээнээс илүү бүтэцтэй байсан: туслах функц, `describe` бүлэг, олон assertion ашигласан. (2) Гэхдээ хоёр алдаа гарсан. Эхнийх нь Logout-ийг `getByRole('link')` гэж таамаглаж бичсэн ч бодит сайт дээр энэ нь `button` байсан тул 6 тест унасан. Хоёр дахь нь сагсны тест заримдаа санамсаргүй унадаг (flaky) байсан. Хуудас солигдох агшинд өмнөх хуудасны 6 бараа DOM-д үлдсэнээс `strict mode violation` алдаа гарч байсан. (3) Эхний алдааг trace болон error-context-ийн хандалтын модыг харж зассан. Хоёр дахийг нь шалгалтыг `cart-list` дотор хязгаарлаж зассан бөгөөд `--repeat-each=5` тохиргоогоор 45/45 давсныг баталгаажуулсан. Эндээс ойлгосон зүйл: AI-ийн бичсэн тест "харагдахдаа зөв" байсан ч бодит сайт дээр ажиллуулж, олон удаа давтаж шалгахгүйгээр итгэж болохгүй.
